Sandbox 02 · Data engineering

A stage is as slow as its slowest task

The driver turns each stage into tasks, one per partition, and hands them to whatever executor cores are free. A stage ends when its last task ends; the next stage can't start until then, because its input is the shuffle files the previous one wrote. Every slow Spark job is one of three things: too many tasks, too few, or one that's much bigger than the others. Set up a job, then step the scheduler.

Engine notes. Same shell as the other sandboxes, with a tick clock. A tick is a unit of work: a task takes one tick of overhead plus one per 25k rows it touches (two total when reading a cached partition). The scheduler is FIFO by stage then task, stages run as soon as their inputs exist, and independent stages run concurrently. Skew puts 40% of the join key on one value. Adaptive execution re-plans a shuffle-consuming stage from the actual map output sizes: it coalesces partitions below 125k rows and splits any partition over twice that, which is how Spark 3 handles both the 200-partition default and skewed joins. Sizes are rows, not bytes; the shapes are what matter.
