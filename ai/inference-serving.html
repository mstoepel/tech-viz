Serving a model is a memory problem wearing a compute costume

Generating one token means reading every weight in the model out of memory. That read costs the same whether you are serving one request or fifty, so the way to make a GPU pay for itself is to have as many sequences as possible riding along on each read. What stops you is not compute — it is the KV cache. Twenty-four requests arrive at once; schedule them.

Engine notes. Same shell as the other sandboxes. This is a real discrete event simulation, not a scripted animation: a step's wall time is 20ms + 0.15ms × batch + 0.05ms × prefill tokens, which encodes the fact that reading the weights dominates and each extra sequence in the batch is nearly free. KV cache is allocated in 16-token blocks; reserved claims prompt + max_tokens on admission the way a naive server does, paged grows a block at a time as vLLM does. When a growing sequence finds no free block the newest running request is preempted and recomputed from scratch, and the tokens it already produced are counted as wasted. The twenty-four requests are a fixed seeded workload with prompts of 30–219 tokens and outputs of 15–139, arriving together as a burst, so every configuration is compared on identical work. Because they all arrive at once, end-to-end latency falls as the batch grows — the cost of batching shows up as time per output token, which is the number to watch.
